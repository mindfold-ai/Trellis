# Technical design

## Boundaries and interpretation
Reuse maintenance API 1.0 and formal_archive_reactivation. Core owns a small reusable public formal-predecessor interpretation/relationship boundary. Recognize canonical completed schema1 as before, plus completed known legacy records with the canonical historical `GitHub issue: https://github.com/<owner>/<repo>/issues/<positive number>` scope. The existing positive legacy classifier owns generation 0; do not fill arbitrary missing fields. The archive record supplies TaskId, never the directory basename.

For legacy, retain raw scope and metadata, accept a valid caller-authored structured Issue source only when repo_ref and number match that scope. Its disposition is caller-owned semantic input, not inferred exact_source or permission to close an Issue. Canonical schema1 source remains exactly preserved. Unsupported/missing legacy scope or an inconsistent source fails explicitly. Reuse this interpretation in projection validation, CLI archive verification/successor inspection and the TS retained-predecessor reader. Python mirrors the same finite format/relationship rule at its existing narrow boundary, with parity assertions; current readers remain unchanged.

## Data flow
Extend only existing inspect-task to accept an omitted expected key: derive and return the positive family/record TaskId/generation from the exact locator, then inspect bindings with that derived key. Supplying a key still asserts an exact match. CLI --task-id and --generation must be supplied together or both omitted. Keep every prepare and formal-inspection input key mandatory. Existing inspect-task obtains exact raw family/key. Formal inspect verifies the selected archive Git facts and uses the shared interpretation, then validates successor provenance, retained bytes, family/key/source and real intermediate completion history. Return existing absent/verified/conflicting facts. A verified archive task_ref reports the successor's current archived location; do not report it as an active key. Prepare takes existing complete projection/artifacts/fact attribution, freezes a plan and creates only a fresh active generation through apply.

Retain original archive and `migration/source-task.json` byte-for-byte, and existing closed `migration/formal-archive-reactivation.json` relation. No new converter, source rewrite, current gates, synthetic Completion/Closure, session/binding changes or semantic owner routing. Projection identity/history validation continues to protect metadata, scope/tree, accepted scope and original-owner legacy fact attribution.

## Recovery and compatibility
Existing frozen operation/guard/recovery mechanisms remain authoritative. Pending has no applied identity. Apply/recover/resume after result loss return the original output key; receiptless inspection separately returns the actual current successor locator/generation after valid lifecycle progress. Check ordinary source mismatches even when private result data is absent. Manual archive_resume preserves generation; native schema2 reopen retains its actual Completion requirement.

## Candidate and rollback
Keep CLI/Core versions matched at the existing candidate version; fixed source SHA plus independent package SHA256 and public maintenance contract identify this build. Pack both packages and install the actual pair into an isolated prefix, verify exact dependency rewriting and public bin/SDK execution. Attach fixed artifacts and evidence to a GitHub prerelease candidate if appropriate for reproducible downstream access; do not publish npm packages. Implementation rollback is the code revert; target-operation rollback stays bounded by existing later-work checks.

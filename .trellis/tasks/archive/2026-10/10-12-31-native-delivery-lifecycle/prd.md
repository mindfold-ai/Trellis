# Native Delivery lifecycle and Task phase migration

## Goal

Make Delivery the native unit of planning, implementation, checking, full review and delivery. Keep Task responsible for stable identity, its overall accepted scope and whole-task acceptance. A user can finish D1, revise plans or validate existing work, deliver D2 and close the whole Task without confusing a commit, a gate pass, a merge or an archive with completion.

## Source and background

Direct Source: [castbox/Trellis#31](https://github.com/castbox/Trellis/issues/31), `exact_source`. The human revised scope on 2026-10-13: #31 is independently accepted upstream work, has no prerequisite relationship with #531, and requires no joint acceptance. Guru owns its own semantic workflow and installed integration; neither its progress nor its evidence blocks this Task. Current code and the required Guru startup sources were read; baseline identities and precise code anchors are in `research/current-contracts.md` and `research/source-anchors.md`. Refresh them before execution.

The current Task schema requires `status`, `inferTaskPhase` derives phase from it, `task.py start` activates execution and `archive` writes completion. Task-level commit/PR fields and planning artifacts cannot describe independent repeated Deliveries. Guru already owns slice readiness, private publication/merge recovery and overall Completion; these capabilities must be consumed and generalized within their ownership boundaries.

## Scope boundaries

In scope: public Task/Delivery schema and APIs; deterministic storage/transitions; native workflow/Skill ownership; current session and candidate applicability; explicit core migration; platform/template/spec alignment; representative controlled marketplace/custom interface compatibility, version diagnosis and upstream-owned evidence.

Out of scope: global unversioned `/task` replacement and destructive legacy execution/API retirement (a future breaking-release workstream); actual Guru integration, private migration and joint acceptance; Guru implementation/gate rewriting in this repository; business code or original business-worktree migration/recovery; deployment/production writes; Issue closure as an automatic effect; publishing a software release; unrequested resource cleanup; arbitrary workflow engines, audit ledgers/event sourcing, persistent authorization, distributed transactions, lock/attack/stress/crash-hardening expansion. The complete release matrix stays with its designated release owner.

## Risks and evidence boundaries

Schema-2 migration spans two languages and multiple platform carriers. Old installations and legacy SDK consumers retain their declared schema until explicit migration; schema-2 execution rejects legacy records rather than inferring phase. Unsupported API/workflow versions are diagnosed before writes. Future breaking retirement must publish replacements/version guidance and prove its own consumer cutover; it is not required for #31 and does not depend on #531.

D1 and D2 upstream increments merged in PR #32 and PR #33. The latter includes the Ubuntu Linear fixture repair and passed actual Ubuntu/Python 3.9 CI at source `bfff3db2`; main squash `ad56d408` has the same tree. Historical reports preserve their former scope and missing-evidence findings. New acceptance is reviewed against this explicit scope revision, with two consecutive complete clean rounds on one final candidate still required. Scope revision does not itself complete or archive the Task or close the Issue.

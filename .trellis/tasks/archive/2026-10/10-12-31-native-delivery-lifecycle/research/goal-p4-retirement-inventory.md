## Findings

### 1. Readiness and the actual remaining work

The accepted retirement gate is `design.md:190-201`: new native lifecycle/migration tests, representative old-install cutover, a consumable Guru candidate actually using the matching API, and public breaking guidance. It does not require Guru Issue CLOSED. The initial opt-in capability may ship separately, but removing the old current contract before these inputs is not the accepted design. `design.md:330-337` expressly permits preparation of migration/inventory/carriers while deferring default retirement.

This inventory refreshes `research/goal-d2-research.md`; its older queue/OpenCode/inventory defects are already addressed in current source. In particular:

- `common/types.py:69-100`, `common/tasks.py:22-79` expose actual accepted-scope/Completion and independent Delivery inventory; no fake schema-2 Task status is generated.
- `common/task_queue.py:75-99` now includes schema-2 whole-Task incomplete inventory; the old claim that all v2 Tasks disappear from pending is no longer current.
- `opencode/lib/session-utils.js:75-85,332-345` now consumes the exact public query for schema 2. Its status fallback is a remaining *legacy branch*, not a current v2 missing implementation.
- Python runtime checks reject selected legacy records in a declared schema-2 workspace and expose unrelated retained records as history-only. They still allow old execution when the installed workflow has no declaration; that normal compatibility path is what P4 must retire.

The parent owns matching Guru readiness and existing candidate/installed/native evidence. This research neither proves nor waives that readiness. A later P4 source candidate must be frozen, packed and paired again where changes affect the consumer; unchanged API numbers alone cannot prove an exact-candidate pair.

### 8. Preparatory source seam decision

There is a useful *design* seam before activation: metadata-only validation/factory shared by v2 and explicit legacy schemas, plus explicit Python history read boundaries. Current v2 still depends on old metadata validation, so the seam must be implemented before or as part of retirement. However it is **not a newly discovered correctness prerequisite for the already frozen opt-in candidate**: existing v2 tests/installed behavior already validate that path, and the explicit TS `/task/legacy-migration` seam is already implemented. The queue/OpenCode preparation formerly requested is complete.

Accordingly no necessary source write needs to interrupt the candidate now being consumed merely to claim preparatory progress. The exact source plan/test dispositions can be reviewed now; default/current export and normal legacy execution removal wait for the accepted readiness gate. Parent may deliberately schedule a separately frozen internal metadata refactor if useful, but must not change what a consumer's candidate fingerprint means or report it as P4 cutover.

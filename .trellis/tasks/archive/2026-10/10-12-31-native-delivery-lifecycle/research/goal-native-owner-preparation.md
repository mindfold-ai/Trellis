# Native semantic-owner sample preparation

This document records the preparation and final scenario corrections. Actual
executed evidence is indexed in `goal-review-loop.md` and
`/tmp/trellis-31-native-owner-HDwXIv/native-final-review-inputs.json`; this
preparation text alone is not an executed result or semantic approval.
The new `goal-native-samples.py` retains invocations and objective snapshots.
It has no automatic gate builder, lifecycle sequence, or inferred verdict.
The invoking AI acts as the declared native owner for each assigned role;
the parent performs independent full Review before readiness/delivery.

## Substantive retained scope

A Git-free sample owns two human-readable service notices and an independent
whole-scope readability verification. First notice: a concise maintenance
notice naming the exact local service window and read-only availability.
Second notice: retained operator-contact guidance. A separate third FAQ draft
is withdrawn before delivery. Both retained notices are UTF-8 business
artifacts; neither is a lifecycle proof-only file.

The first Delivery initially plans a maintenance notice, then the scope owner
revises its window before delivery. The same Delivery must return to Planning
and implement the current content. Parent Review sees the actual original and
revised scope/plan, exact artifact, and fresh Check evidence. A second Delivery
actually delivers the operator-contact artifact with independent planning and
applicable gates. A third Delivery plans the FAQ, but scope later withdraws the
FAQ obligation entirely; the
current-stage and scope owners explain why it is stopped, not delivered.

Known outcomes do not satisfy the unallocated readability verification. The
Completion owner first returns evidence_pending without a completion write.
After independently reading the whole notice for clarity and verifying the
specified wording, it invokes Completion without a new Delivery or content
change. Closure is separately no_mutation. An ordinary failed removal of an
unrelated non-empty temporary directory demonstrates that cleanup failure
does not revoke Completion.

Archive/history/reopen follow the installed public API. Two explicit renames
before archive exercise artifact-origin stability and live context manifests.
Reopen retains both accepted notice requirements and adds current validation of
the still-retained bytes. Fresh Completion judges those current requirements and
old delivered outcomes, rather than treating old gates or Closure as current
approval. It creates no new Delivery and no execution binding.

## Real local Git sample

A separate temporary repository owns a concrete operator notice committed on
a feature branch and an independent operator-contact baseline improvement on
main. A real merge integrates the baseline. The implementation owner identifies
the actual changed base/candidate and routes to fresh Check, preserving the
same Delivery. Candidate paths include the entire reviewed slice; the parent
reads the full intended base-to-HEAD range. Check and first full Review operate
on a clean committed candidate and make no empty/proof-only commit. Delivery
records the actual immutable local commit only after parent Review/readiness.
Its original owner recovers a lost output with the identical result identity,
while observing unchanged HEAD, commit count, candidate and terminal fact.

## Execution boundary

Execute only after the parent supplies the frozen packaged candidate, retaining
its exact path/hash/source identity and actual installed workflow declaration.
All sample resources and invocation evidence stay under new /tmp roots. No
product Task migration, repo commit/build/push, Guru writes, external messages,
remote transactions or actual resource cleanup is included. Scenarios pause at
reviewing for independent Review and resume only after the parent verdict.
Guru PR transaction and installed semantic scenarios remain Guru-owned;
these native samples cannot satisfy those boundaries or whole-Issue clean rounds.

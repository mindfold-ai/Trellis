# Native semantic-owner acceptance scenarios

These controlled installed scenarios supplement runtime fixtures. They do not
replace Guru's private/installed evidence or create lifecycle facts in this
repository's current Task. Execute only against the frozen corrected package
candidate in temporary roots. An AI owner must make each semantic decision
before calling its closed recording API; a script cannot derive a pass from
phase, file existence or a fixed fixture label.

## A. Scope revision, same Delivery rework and withdrawal

Accept a Task scope containing two retained text outputs, a draft FAQ slice and
one acceptance verification. Plan an actual first Delivery and implement its text artifact.
Before delivery, revise the required artifact text and return to the earliest
affected Planning owner with the same Delivery ID. Inspect which candidate,
plan, authority and downstream results changed; keep actual commit/file facts.
Fresh Planning/implementation/Check/full Review/readiness then records the real
manual outcome. Independently plan, implement, review and actually deliver a
second retained operator-contact output. Both deliveries keep distinct plans
and identities. Create a third FAQ slice, then revise the whole authority to
withdraw that obligation. The scope and current-stage owners stop that slice;
verify it is stopped rather than delivered, identity survives,
and the execution selection clears. Whole Completion assesses the revised
scope and any unallocated verification, independently of both known outcomes.

## B. Unallocated evidence, Completion-only refresh and cleanup failure

With all known Deliveries delivered/stopped, deliberately leave a declared
whole-scope verification outstanding. The Completion owner reads the actual
scope/outcomes and exits evidence_pending with no completion record. It does
not allocate an empty Delivery. Perform the outstanding read-only verification,
then invoke Completion again on unchanged scope/content and record only its
actual completed result. Record no_mutation Closure separately. Execute an
ordinary failing `rmdir` against a non-empty disposable, unrelated directory;
verify it cannot
alter Completion or manufacture another Delivery/result. Source Issue actions
and real resource cleanup are outside this sample.

## C. Archive, history and validation-only reopen

Archive the completed sample through the installed public command. Read its
Delivery/history via an explicit archive path. The Task owner formally reopens
the same identity with a new generation and current authority. Verify retained
old facts are unchanged, execution selection remains absent and no Delivery is
created. The fresh Completion owner independently judges applicability of the
retained artifact to the new scope and performs current validation; it may
record generation-specific Completion without redelivery. Old approvals and
Closure are not current-generation pass. Exercise more than one relocation so
artifact-origin normalization is observed in actual installed use.

## D. Clean candidate after real base integration

Use a temporary real Git repository with a feature artifact commit and an
independent baseline change. Integrate the baseline through a real merge. The
semantic owner determines the affected base/candidate inputs, routes to fresh
Check and hands the still-clean committed candidate to its first full Review.
The independent reviewer reads the complete base-to-head range. Record the
real local_commit outcome only after applicable Review/readiness. The commit
count and HEAD before/after Check/Review/delivery must be unchanged; neither an
empty commit nor a proof-only commit is created. Recover a deliberately lost
local result output through its original owner and identical recorded identity,
with no new commit. Guru owns the real PR Publish/Merge transaction counterpart.

## Evidence to retain

For every invocation retain the package/source candidate identity, actual
workflow declaration, Task/Delivery/generation, scope and plan refs, owner
reasoning/verdict, exact candidate/base and real artifact/commit facts, command
outputs and before/after mutation observations. Review remains independent of
the implementation owner. No scenario is marked PASS until it has run and its
actual evidence has been inspected. External host tests remain unverified if
the host is unavailable.

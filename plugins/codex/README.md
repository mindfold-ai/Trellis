# Trellis Codex plugin

This companion plugin registers Trellis's Codex hook entry points once, so a
Codex user can review the plugin hook definitions instead of approving an
equivalent project hook in every repository.

## Install

Add the Trellis repository as a Codex marketplace, then install and enable the
**Trellis** plugin. The repository includes the marketplace metadata Codex
needs to discover `plugins/codex`:

```sh
codex plugin marketplace add https://github.com/mindfold-ai/Trellis.git
codex plugin add trellis@trellis
```

For a local checkout while developing the plugin, use its absolute path
instead:

```sh
codex plugin marketplace add /path/to/Trellis
codex plugin add trellis@trellis
```

The plugin directory contains the `.codex-plugin/plugin.json` manifest and
does not need to be copied into a project.

In each project, run the normal setup when Trellis is not initialized yet:

```sh
trellis init --codex
```

Then opt into plugin-owned hooks in `.trellis/config.yaml`:

```yaml
codex:
  hook_mode: plugin
```

Plugin mode disables the repository-local Codex hooks. Before removing the
managed `.codex/hooks.json` file and `.codex/hooks/` directory, back up or move
any entries you added yourself; preserve those user-owned hooks separately and
remove only the Trellis-managed hook definitions. With plugin mode active,
later `trellis init` and `trellis update` runs omit the Trellis paths instead of
regenerating them. Keep the default
`hook_mode: project` when the plugin is not installed or the Codex surface does
not support plugins.

The plugin is currently intended for Codex App/CLI surfaces that support
plugins. Codex IDE integrations without plugin support continue using the
project-local hooks generated by `trellis init --codex`.

## What it does

The plugin registers `SessionStart`, `UserPromptSubmit`, and `SubagentStart`
hooks. Its small dispatcher finds the nearest repository containing `.trellis/`
and runs the corresponding reviewed runtime from the plugin bundle only when
that repository sets `codex.hook_mode: plugin`. Repositories with the default
`project` mode are ignored by the plugin, leaving their project-local hooks as
the sole owner. The plugin never executes a hook from the active repository;
the bundled runtimes only read workflow state and customization from it, and
the dispatcher exits quietly for non-Trellis repositories.

Trellis state, specs, skills, and agent profiles remain project-local. The
executable hook implementation lives in the plugin and is kept byte-identical
to the shared runtime used by the project-hook fallback.

## Trust and permissions

Plugin hook review is still required when the plugin is installed or enabled.
The benefit is that the stable plugin hook definition can be reviewed once;
changing that definition may require review again. Plugin approval is separate
from command/tool approval, sandbox permissions, and access to external
services.

The existing `.codex/hooks.json` integration remains the default fallback, so
projects can use Trellis without the plugin. Before disabling or removing the
plugin from a project using plugin mode, change `hook_mode` back to `project`
and run `trellis update` to restore the local workflow hooks.

This is an initial companion-plugin proposal tracked in
[Trellis issue #593](https://github.com/mindfold-ai/Trellis/issues/593).
